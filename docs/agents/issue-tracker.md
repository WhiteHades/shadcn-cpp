# Issue tracker

Use the numbered Markdown files under `docs/issues` as the current tracker. `docs/spec.md` is the shared specification. Each issue records dependencies, scope, acceptance and evidence. No remote issues exist yet.

Select the first unfinished issue whose dependencies have evidence. Split large component batches into one-component issues before implementation. Use the documented source pin and add a failing public-interface test for each behaviour.

After GitHub publication, the maintainer may move these records to GitHub issues. Record the remote issue number in the local file before using it as the tracker. Do not claim that an issue was created without a successful GitHub write.
